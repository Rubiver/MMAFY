## 사용 시기

테스트가 실패하거나, 테스트 케이스를 작성해야 하거나, 테스트 기반 개발(TDD) 사이클이 필요한 모든 상황에 활성화합니다.

## 핵심 원칙

### 1. 테스트케이스 변경은 최종 수단

- 테스트케이스를 수정하려면 **합리적인 이유**가 있어야 합니다.
- 명백히 잘못된 실제 결과임에도 테스트케이스를 수정해서 억지로 통과시키지 마세요.
- 테스트케이스를 변경해야 한다고 판단되면, 그 이유를 명시하고 사용자에게 보고하세요.
- 테스트가 실패할 때 먼저 의심해야 할 것은 **테스트 대상 코드**입니다.

### 2. 원인 파악 → 수정 → 검증 사이클

1. 테스트 실패 메시지 분석
2. 실패 원인이 버그인지, 테스트 오류인지 판단
3. 코드 수정 후 재테스트
4. 모든 테스트 통과 확인

### 3. 언어 및 기술에 맞는 테스트 프레임워크 사용

| 언어/프레임워크 | 테스트 프레임워크 | 실행 명령 |
| ---------------- | ------------------ | ---------- |
| JavaScript/TypeScript (Node.js) | Jest, Vitest, Mocha | `npm test`, `yarn test`, `pnpm test` |
| React | Jest + Testing Library | `npm test` |
| Vue | Vitest + Testing Library | `npm run test` |
| Next.js | Jest + Testing Library | `npm test` |
| Python | pytest | `pytest` 또는 `python -m pytest` |
| Java | JUnit 5 | `mvn test` 또는 `gradle test` |
| Go | testing 패키지 | `go test ./...` |
| Ruby | RSpec | `bundle exec rspec` 또는 `rspec` |
| C# | xUnit / NUnit / MSTest | `dotnet test` |
| Rust | Cargo 테스트 | `cargo test` |
| 웹 UI (브라우저) | Playwright | `npx playwright test` |

## 웹 클라이언트 검증

웹 클라이언트 프로젝트의 경우 **Playwright MCP**를 사용하여 UI 검증을 수행합니다:

1. 테스트 실패 원인이 UI 렌더링 문제인 경우 Playwright MCP 로 화면 상태 확인
2. 수정 적용 후 Playwright MCP 로 재검증
3. 주요 뷰포트(모바일 375px, 태블릿 768px, 데스크톱 1280px+) 에서 검증

## 실행 절차

### 단계 1: 테스트 실행 및 결과 분석

1. 프로젝트의 테스트 실행 명령 확인 (`package.json`, `pom.xml`, `Cargo.toml` 등)
2. 테스트 실행
3. 실패한 테스트의 에러 메시지, 스택 트레이스 분석

### 단계 2: 원인 판단

| 실패 유형 | 원인 | 대응 |
| ---------- | ------ | ------ |
| `AssertionError` / 실패한 어설션 | 실제 코드가 기대 동작과 다름 | **코드 수정** |
| `TypeError` / `ReferenceError` | 코드 버그 (undefined, null 등) | **코드 수정** |
| `TimeoutError` | 비동기 처리 문제 | **코드 수정** |
| import/require 실패 | 의존성 또는 경로 문제 | **설정/코드 수정** |
| 테스트 데이터 문제 | 테스트용 가짜 데이터 오류 | **테스트 데이터 수정** |
| 어설션 조건 오류 | 테스트케이스의 기대값/조건 틀림 | **테스트케이스 수정 (이유 명시)** |

### 단계 3: 코드 수정

1. 원인이 명확한 경우 직접 수정
2. 수정 후 해당 테스트만 우선 재실행
3. 통과 확인 후 전체 테스트 재실행

### 단계 4: 전체 테스트 통과 확인

1. 모든 테스트가 통과하는지 확인
2. 새로운 테스트 실패가 생기지 않았는지 확인 (레거시 테스트 깨지지 않았는지)

## 테스트케이스 변경 시 고려사항

테스트케이스를 수정해야 한다고 판단되면 다음을 확인하세요:

1. **문서의 명세와 일치하는가?** (PRD, DETAIL_SPEC, API 문서 등)
2. **실제 비즈니스 로직과 일치하는가?**
3. **다른 테스트와 일관되는가?** (같은 기능의 다른 테스트와 모순되지 않는가)
4. **에지 케이스를 적절히 커버하는가?**

테스트케이스를 변경할 때는 변경 이유를 주석이나 메시지에 명시하세요.

## 예외 상황 처리

| 상황 | 대응 |
| ------ | ------ |
| 테스트 프레임워크가 설치되지 않음 | 프레임워크 설치 후 진행 |
| 테스트 실행 중 환경 변수 필요 | 필요한 환경 변수 확인 및 설정 |
| 의존성 문제로 테스트 실행 불가 | 의존성 해결 후 진행 |
| 테스트가 너무 많아서 시간이 오래 걸림 | 실패한 테스트만 우선 수정, 전체는 나중에 검증 |
| 레거시 테스트가 이미 실패 중 | 해당 테스트는 무시하고 새로운 테스트만 수정 (보고는 필수) |

## 규칙

- 모든 설명과 주석은 한국어로 작성합니다.
- 중국어 한자를 절대 사용하지 않습니다.
- 테스트케이스 변경은 최소한으로, 이유를 명시합니다.
- 코드 수정 후 반드시 전체 테스트 재실행으로 회귀 검증합니다.
- 웹 클라이언트 프로젝트는 Playwright MCP 로 UI 검증합니다.
