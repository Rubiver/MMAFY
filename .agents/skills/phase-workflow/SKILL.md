## 사용 시기

- 사용자가 특정 phase 의 구현을 시작하거나 전체 workflow 를 실행하라고 요청할 때
- 프로젝트의 단계별 개발을 순차적으로 진행해야 할 때
- phase 의 시작, 진행, 완료 전체 과정을 오케스트레이션해야 할 때

## 개요

각 phase 는 총 **여섯 단계**로 구성됩니다. 에이전트는 각 단계로 진입할 때 **반드시 해당 단계 스킬의 SKILL.md 를 읽어야 합니다**.

### 일반 phase 의 여섯 단계

1. **phase-executor** — 페이즈 문서에 정의된 작업을 분석하고 구현
2. **apply-ui-styling** — UI 스타일링 판단 및 적용 (웹 클라이언트인 경우)
3. **auto-test-fixer** — 테스트 실패 원인 파악 및 코드 자동 수정
4. **critical-bug-review** — 소스코드 및 로그 기반 버그 탐지 및 보고
5. **phase-verifier** — phase 완료 기준 체크리스트 검증
6. **harness-compounder** — 실행 결과 분석, 문제 기록, 개선 제안, 완료 체크박스 갱신

### 마지막 phase 의 별도 절차

마지막 phase 는 여섯 단계를 무시하고 다음 **세 단계**를 따릅니다:

1. **전체 코드 검토** — 잔존 버그 확인 (웹 클라이언트라면 Playwright MCP 사용)
2. **전체 코드 리팩토링** — 코드 정리 및 개선
3. **전체 코드 재검토** — 리팩토링 후 잔존 버그 재확인

## 실행 절차 — 일반 phase

### 단계 1: phase-executor

1. `phase-executor` 스킬의 SKILL.md 읽기
2. 해당 phase 문서(`phases/phase-N.md`) 에 정의된 작업 분석
3. 구현 계획 수립 및 실행
4. 구현 완료 후 다음 단계로 진행

### 단계 2: apply-ui-styling

1. `apply-ui-styling` 스킬의 SKILL.md 읽기
2. 프로젝트 성격 판단 (서버 / 웹 / 기타)
3. 웹 클라이언트인 경우 Tailwind CSS 스타일링 적용
4. Playwright MCP 로 백그라운드 검증
5. 완료 후 다음 단계로 진행

### 단계 3: auto-test-fixer

1. `auto-test-fixer` 스킬의 SKILL.md 읽기
2. 테스트 실행 및 실패 분석
3. 코드 수정 및 재테스트
4. 모든 테스트 통과 확인
5. 완료 후 다음 단계로 진행

### 단계 4: critical-bug-review

1. `critical-bug-review` 스킬의 SKILL.md 읽기
2. 로그 파일 및 소스코드 분석
3. [BLOCKING] / [NIT] 형식으로 문제 보고
4. BLOCKING 이 있으면 수정 후 재실행
5. 완료 후 다음 단계로 진행

### 단계 5: phase-verifier

1. `phase-verifier` 스킬의 SKILL.md 읽기
2. phase 문서의 완료 기준 체크리스트 확인
3. 각 항목 검증 (O/X 판정)
4. FAIL 시 자체 수정 후 재검증
5. 최종 결과 보고
6. 완료 후 다음 단계로 진행

### 단계 6: harness-compounder

1. `harness-compounder` 스킬의 SKILL.md 읽기
2. 실행 결과 분석 및 문제점 기록
3. `unsolved-compound-log.md` / `solved-compound-log.md` 관리
4. 개선 제안 도출
5. 완료 체크박스 갱신, git commit, resume.md 갱신
6. phase 완료

## 실행 절차 — 마지막 phase

마지막 phase 번호를 식별한 후 다음 세 단계를 순차적으로 실행합니다:

### 단계 1: 전체 코드 검토

1. 프로젝트 전체 코드베이스를 검토
2. 잔존 버그를 탐지하고 보고
3. **웹 클라이언트인 경우**: Playwright MCP 를 활용하여 UI 렌더링, 상호작용, 사용자 흐름 검증
4. 탐지된 문제는 [BLOCKING] / [NIT] 형식으로 분류

### 단계 2: 전체 코드 리팩토링

1. 검토에서 발견된 BLOCKING 문제 수정
2. 코드 품질 개선 (가독성, 일관성, 중복 제거)
3. 불필요한 리팩토링은 금지 — 요청된 범위만 수정

### 단계 3: 전체 코드 재검토

1. 리팩토링 후 전체 코드 재검토
2. 잔존 버그가 없는지 확인
3. 모든 테스트 재실행 및 통과 확인
4. 최종 결과 보고

## 규칙

1. **SKILL.md 읽기 의무화**: 각 단계로 진입할 때 반드시 해당 단계 스킬의 SKILL.md 를 읽어야 합니다. 읽지 않고 넘어가면 안 됩니다.
2. **순차 실행**: 각 단계는 순서대로 실행합니다. 다음 단계는 이전 단계가 완료된 후에만 시작합니다.
3. **한국어 작성**: 모든 설명, 주석, 보고는 한국어로 작성합니다. (기술 용어는 영문 유지 가능)
4. **중국어 금지**: 중국어 한자를 절대 사용하지 않습니다.
5. **수정 범위 제한**: 각 단계에서 수정하는 코드는 해당 단계의 목적에만 국한합니다. 인접 코드 리팩토링 금지.
6. **테스트 재실행**: 코드 수정 후에는 반드시 관련 테스트를 재실행하여 통과 확인합니다.
7. **마지막 phase 예외**: 마지막 phase 는 여섯 단계를 무시하고 세 단계 절차를 따릅니다.
8. **Playwright MCP**: 마지막 phase 의 전체 코드 검토 시, 웹 클라이언트라면 Playwright MCP 를 반드시 사용해야 합니다.

         │
         ▼
┌──────────────────┐
│ 3. auto-test-fixer │ ← SKILL.md 읽기 → 테스트 통과
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ 4. critical-bug-review│ ← SKILL.md 읽기 → 버그 탐지/수정
└────────┬─────────┘
         │

         │
         ▼

         │
         ▼

│ 3. 전체 코드 재검토   │  ← 잔존 버그 확인 + 테스트 재실행

         ▼

## 참고

- 이 스킬은 오케스트레이션 전용이며, 실제 구현/검증/수정은 각 하위 스킬이 담당합니다.
- 각 단계 스킬은 독립적으로 동작하며, 필요시 재시도가 발생할 수 있습니다.
- 재시도가 발생하면 `harness-compounder` 가 패턴을 기록하고 다음 phase 에 이관합니다.
- `phase-executor` 는 `./docs/unsolved-compound-log.md` 를 읽어 미완료 문제를 확인합니다.
